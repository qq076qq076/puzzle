# 08｜技術框架、套件與效能策略

## 1. 選擇結論

### 主要方案

**Phaser 4.2.1 + Vite + 原生 JavaScript ES Modules**

這個方案的排序是：

1. 先使用 GPU 優先的 WebGL 渲染與批次繪製。
2. 再使用 Phaser 已經提供的 Tilemap、Scene、Camera、Animation、Input 與 Arcade Physics，降低自行實作引擎的風險。
3. 使用 Vite 管理模組、開發伺服器與生產打包。
4. 不引入 React、Vue、ECS 框架、重量級物理套件或虛擬搖桿套件。

Phaser 官方目前的 Phaser 4 發行頁列出的最新版本為 4.2.1；Phaser 4 的 WebGL Renderer、GPU Sprite／Tilemap Layer 與現代瀏覽器支援符合本遊戲的效能優先目標。[Phaser 4 發行頁](https://phaser.io/download/phaser4)、[Phaser 4 Renderer](https://phaser.io/news/2026/04/phaser-4-renderer-faster-cleaner-and-built-for-modern-games)

## 2. 套件清單

### 執行期套件

| 套件 | 版本策略 | 用途 | 是否必要 |
|---|---|---|---|
| `phaser` | 鎖定 `4.2.1` | 遊戲主框架、WebGL／Canvas、Scene、Camera、Tilemap、Animation、Input、Sound | 必要 |

Phaser 的 Tilemap 可以載入 Tiled JSON、使用多層 TilemapLayer，並支援可見區域裁切；Arcade Physics 提供矩形／圓形碰撞，適合本遊戲的俯視角移動與近戰碰撞。[Phaser Tilemap](https://docs.phaser.io/api-documentation/class/tilemaps-tilemaplayer)、[Phaser Physics](https://docs.phaser.io/api-documentation/physics)

### 開發與測試套件

| 套件 | 版本策略 | 用途 | 是否必要 |
|---|---|---|---|
| `vite` | 鎖定 lockfile 版本 | 開發伺服器、ESM、打包、資產路徑處理 | 必要 |
| `@playwright/test` | 鎖定 lockfile 版本 | 驗證桌面鍵盤、手機橫向、觸控按鈕與旋轉提示 | 第二階段加入 |
| `node:test` | 使用 Node 內建 | 測試房間種子、威脅點數、Buff、傷害公式 | 不另裝套件 |

Vite 的生產建置會輸出適合部署的靜態資產，且支援原生 JavaScript 模板，不需要為了使用 Phaser 引入前端 UI 框架。[Vite 官方指南](https://vite.dev/guide/)

### 外部製作工具，不打包進遊戲

| 工具 | 用途 |
|---|---|
| Tiled | 製作普通房與 Boss 房模板，輸出 JSON Tilemap |
| 圖像編輯器 | 將 PSD 匯出為 PNG、整理 spritesheet 或 atlas |

Tiled 只在開發期間使用；玩家下載的遊戲只包含處理後的 PNG／atlas 與 JSON，不包含 PSD。

## 3. 為何不選其他方案

| 方案 | 優點 | 不選原因 |
|---|---|---|
| 原生 Canvas 2D | 初始程式碼少 | 必須自行處理 Tilemap、動畫、攝影機、碰撞、物件池與資產管理；長期總成本較高 |
| PixiJS + 自製遊戲系統 | 渲染控制力高 | 仍要自行補 Scene、Tilemap、Physics、Input 與動畫管理；不符合「第二考慮簡單實現」 |
| Phaser 3 | 生態成熟、文件多 | 新專案沒有歷史包袱；目前以 Phaser 4.2.1 的新 WebGL Renderer 為效能優先方案 |
| Matter.js | 物理功能完整 | 本遊戲不需要關節、彈性或複雜剛體；額外計算與 API 複雜度沒有價值 |
| React／Vue | UI 開發方便 | 遊戲世界不應以 DOM 元件逐物件渲染，會增加狀態同步與更新成本 |
| Godot Web Export | 工具完整 | 會增加引擎匯出、載入與部署複雜度，不符合目前純瀏覽器遊戲專案的工作方式 |

## 5. Phaser 設定

### 渲染

- 使用 `Phaser.AUTO`，優先使用 WebGL；不支援 WebGL 時才退回 Canvas。
- 不直接強制 `WEBGL`，避免低階或特殊瀏覽器完全無法啟動。
- 遊戲邏輯基準尺寸先定為 960×540，保持 16:9 橫式比例。
- 使用 Phaser Scale Manager 的 `FIT` 與 `CENTER_BOTH`，讓畫面保持比例並完整置中。[Scale Manager](https://docs.phaser.io/phaser/concepts/scale-manager)
- 像素素材使用 nearest-neighbor／關閉平滑縮放；所有素材以整數倍或整數像素位置繪製。
- 使用 Camera culling，只處理目前可見的 Tilemap 與遊戲物件。
- MVP 不開啟全畫面濾鏡、即時光照、模糊或大量粒子，避免破壞 sprite batching。

### 物理與碰撞

- 使用 Phaser Arcade Physics，不使用 Matter.js。
- 玩家、敵人與障礙物使用矩形或圓形 body。
- 地城牆壁與不可行走區使用靜態 Tilemap collision layer。
- 近戰攻擊不建立永久物理 body；只在攻擊有效幀，以玩家位置、面向、距離與扇形計算命中。
- 閃避使用自訂位移狀態與無敵計時，不依賴物理引擎的推力或剛體。
- 陷阱與投射物使用物件池，避免每次生成與銷毀造成垃圾回收尖峰。

### 更新迴圈

- 遊戲邏輯使用固定 60Hz 更新，渲染由 Phaser 每幀呈現。
- 每幀先讀取輸入快照，再執行玩家、敵人、碰撞、傷害、房間狀態與獎勵狀態更新。
- 遊戲暫停時停止戰鬥計時與敵人 AI，不只停止畫面繪製。
- 隨機內容只在房間生成階段產生；戰鬥中不以非決定性亂數改寫房間規則。

## 6. 操作實作

### 電腦版

- 只註冊鍵盤輸入：WASD／方向鍵、Space、Shift、Esc／P。
- Phaser 的滑鼠輸入關閉，不註冊滑鼠移動、點擊、滾輪或拖曳事件。
- 選單、Buff 說明與暫停畫面使用鍵盤完成；房間獎勵使用左／右方向鍵選擇，再用攻擊鍵確認。

### 手機版

- 使用 Phaser Touch／Pointer 輸入，但只接受 `pointerType === "touch"` 的事件；滑鼠事件一律忽略。獎勵畫面以右側虛擬搖桿的左右方向選取，左側攻擊按鈕確認。
- 左側建立攻擊與閃避按鈕，右側建立單一虛擬搖桿。
- 虛擬搖桿同時提供移動方向與玩家面向，不再提供第二個瞄準搖桿。
- 不引入第三方 joystick 套件；自行實作一個小型 touch-control system，降低依賴、事件轉發與樣式衝突。
- 啟動時嘗試使用 Screen Orientation API 鎖定 `landscape`；若無法鎖定，顯示橫向提示並暫停遊戲。[Phaser Scale Manager](https://docs.phaser.io/api-documentation/class/scale-scalemanager)

## 7. 資產與載入策略

- PSD 只作為編輯來源，執行期不載入 PSD。
- 將同一主題的角色與物件整理成 atlas 或 spritesheet，降低 texture bind 與 draw call。
- BootScene 只負責建立最小啟動環境；PreloadScene 統一載入第一階段素材與字型。
- BossScene 在第 5 間普通房完成後才以 dynamic import 載入，避免玩家尚未進入 Boss 前解析整個 Boss 模組。
- 不在每個房間重複載入圖片；所有素材在 PreloadScene 後進入 Phaser Texture Cache。
- 房間 JSON 只保存地形、碰撞、生成點、出口與獎勵插槽，不把完整怪物狀態寫進靜態地圖。
- 清理房間時銷毀或回收敵人、投射物與特效物件，但保留共用 Texture Cache。

## 8. 效能預算

第一階段以中階手機 60 FPS 為目標，不以桌面高階 GPU 的結果作為唯一標準。

| 指標 | 預算 |
|---|---:|
| 目標更新率 | 60 FPS |
| 普通房同時活躍敵人 | 最多 12 個 |
| Boss 房同時活躍敵人與支援物 | 最多 16 個 |
| 同時存在的投射物／陷阱效果 | 最多 32 個 |
| 每次房間切換的額外載入 | 0 張重複圖片；只載入必要 JSON |
| 遊戲世界中的 DOM 遊戲物件 | 0；只允許固定 UI／方向提示 |
| 連續 10 分鐘遊玩 | 不應持續增加記憶體 |

若效能不足，依序處理：

1. 降低特效與粒子數量。
2. 確認所有角色使用 atlas／spritesheet。
3. 減少每幀尋路與碰撞檢查，改用房間內空間分區。
4. 降低 Canvas 顯示解析度但維持遊戲邏輯尺寸。
5. 最後才考慮減少同時敵人數；不可先犧牲核心戰鬥手感。

## 9. 儲存與部署

- 第一階段使用 `localStorage` 儲存音效設定、上次選擇與最近 Run Seed。
- 活躍 Run 狀態先保存在記憶體；完成房間或離開頁面前再寫入必要的統計資料。
- 暫不接 Firebase、雲端同步或即時連線，避免網路與後端成為遊戲啟動瓶頸。
- 使用 npm lockfile 鎖定版本，部署前用 `npm ci` 與 `npm run build`。
- 生產環境只部署 Vite 輸出的靜態檔案；不依賴 CDN 才能啟動遊戲。

## 10. 第一階段實作順序

1. 建立 Vite vanilla 專案與 Phaser 4.2.1，確認 WebGL／Canvas 啟動與橫式縮放。
2. 匯入一個普通房 Tilemap、騎士與一個哥布林，完成鍵盤移動與近戰。
3. 加入 Arcade Physics、牆壁碰撞、閃避與受傷無敵。
4. 加入房間模板選擇、種子與五個普通房流程。
5. 加入怪物資料、AI、威脅點數、獎勵與 Buff。
6. 加入第六房 Boss、Boss 階段與勝利畫面。
7. 加入手機橫式遮罩、左側攻擊／閃避與右側虛擬搖桿。
8. 以中階手機測試 60 FPS、記憶體是否持續增加與連續 Run 穩定性。
