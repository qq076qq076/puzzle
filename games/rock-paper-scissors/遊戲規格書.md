# 剪刀石頭布（P2P 純前端版）遊戲規格書

> 文件版本：1.0  
> 文件狀態：MVP 實作規格  
> 目標平台：桌面與行動版現代瀏覽器

## 1. 專案目標

建立一款不需自建應用後端的雙人剪刀石頭布遊戲。兩位玩家可以使用不同裝置、不同網路，並從不同網域開啟前端頁面後進行遊戲。

核心目標：

- 遊戲頁面可部署在任意 HTTPS 靜態網站。
- 使用 WebRTC DataChannel 讓兩個瀏覽器直接傳送遊戲資料。
- 不架設配對或遊戲應用後端。
- 使用「邀請網址」交換連線資訊：QR Code 與複製按鈕都指向同一個帶邀請碼網址。
- 使用 commit-reveal 協定，避免後出拳的玩家看到對手選擇後作弊。
- 不收集帳號、個人資料與永久戰績。

### 1.1 「純前端」的範圍

本專案的純前端指不開發與不維運應用 API、資料庫或配對伺服器。為了穿越 NAT，WebRTC 仍可能使用經授權的第三方 STUN 服務。

本版已加入第三方 TURN 作為直連失敗時的中繼 fallback。中繼模式會使遊戲資料經過第三方伺服器，但 WebRTC 仍以 DTLS 加密。若未來上線要求更高，應改用自己管理的 TURN 與限時憑證。

## 2. 遊戲範圍

### 2.1 MVP 功能

- 建立遊戲與加入遊戲。
- 開啟邀請網址後自動匯入 WebRTC Offer；Answer 仍以 QR Code 或複製貼上回傳給主機。
- 顯示連線狀態、玩家角色與回合狀態。
- 雙方選擇剪刀、石頭或布。
- 以 commit-reveal 驗證雙方選擇。
- 判定單把結果。
- 單把結束後，由雙方選擇「下一把」或「退出」。
- 只有雙方都選擇「下一把」時才繼續遊戲。
- 支援重新配對、斷線提示與離開遊戲。

### 2.2 不在 MVP 範圍

- 帳號、好友、排行榜與永久戰績。
- 公開大廳、隨機配對或觀戰。
- 伺服器權威裁定與斷線重連。
- 防止修改前端程式、假造戰績或故意斷線。

## 3. 技術說明

### 3.1 技術選擇

- **HTML5 / CSS / JavaScript**：遊戲界面、狀態管理與互動。
- **WebRTC `RTCPeerConnection`**：建立兩個瀏覽器之間的 P2P 連線。
- **WebRTC `RTCDataChannel`**：使用可靠、有序模式傳送 JSON 遊戲訊息。
- **Web Crypto API**：使用 `crypto.getRandomValues()` 產生 nonce，並使用 SHA-256 建立出拳承諾值。
- **QR Code 編碼／掃描**：用於不同裝置之間交換配對資料。
- **CompressionStream（可選）**：在瀏覽器支援時壓縮 SDP，降低 QR Code 的容量壓力。

DataChannel 設定應保留預設的可靠、有序傳輸，因為遊戲訊息量小，正確性比低延遲更重要。

### 3.2 系統架構

```text
靜態網站 A                                  靜態網站 B
玩家 A 瀏覽器                              玩家 B 瀏覽器
     |                                              |
     |--- 邀請網址（QR Code／複製）---------->|
     |<-- Answer（QR Code／複製貼上）---------|
     |                                              |
     |<======= WebRTC DataChannel（DTLS）=========>|
     |          commit / reveal / result             |
     |                                              |
                  STUN（NAT 路徑探測）
             TURN（可選，直連失敗時中繼）
```

兩端頁面不必來自同一網域。只要雙方使用相容的訊息協定與版本，即可透過 DataChannel 溝通。遊戲資料不使用 HTTP 向對方網域發出請求，因此不依賴一般的 CORS 放行設定。

### 3.3 部署與瀏覽器要求

- 正式環境必須使用 HTTPS。
- 本機開發可使用 `localhost`。
- 使用相機掃描 QR Code 時，瀏覽器必須取得相機權限。
- 若玩家拒絕相機權限，仍可使用複製貼上完成配對。
- 需支援 `RTCPeerConnection`、`RTCDataChannel`、`crypto.subtle` 與 `crypto.getRandomValues()`。

### 3.4 配對與 Signaling

本專案不使用 signaling server；主機以邀請網址分享 Offer，加入者自動匯入後，再由玩家交換 Answer。

1. 主機建立 `RTCPeerConnection` 與 DataChannel。
2. 主機建立 Offer，設定 local description，並等待 ICE gathering 完成。
3. 主機將完整 Offer 包裝成配對封包，放進帶 `#invite=` 片段的邀請網址中，再同時產生 QR Code。
4. 加入者開啟邀請網址後自動匯入 Offer，建立並回傳 Answer。
5. 主機匯入 Answer，等待 DataChannel 轉為 `open`。
6. 雙方完成 `hello` 與協定版本檢查後開始遊戲。

建議採用 non-trickle ICE，先等待 ICE candidate 收集完成再產生配對封包，避免玩家多次交換 candidate。

實際部署可在載入 `script.js` 前設定 `window.RPS_ICE_SERVERS`，用自己管理的 STUN/TURN 清單覆蓋預設清單。TURN 應使用限時憑證，不要把永久密碼當成前端公開設定。

QR Code 容量有限；完整 SDP 與 ICE candidates 可能太大。實作時應：

- 去除非必要的 JSON 空白。
- 壓縮後再使用 Base64URL 編碼。
- 超過單一 QR Code 容量時，依然提供邀請網址複製按鈕；不在畫面上展示完整邀請字串。
- 匯入前驗證資料格式、長度與協定版本。

### 3.5 配對封包格式

```json
{
  "app": "rock-paper-scissors",
  "protocolVersion": 1,
  "kind": "offer",
  "sessionId": "random-session-id",
  "description": {
    "type": "offer",
    "sdp": "..."
  },
  "createdAt": 1786464000000
}
```

`kind` 僅能為 `offer` 或 `answer`。匯入時應拒絕錯誤應用名稱、不支援的協定版本、過期時間或超過限制長度的資料。

### 3.6 DataChannel 訊息協定

每個訊息使用 JSON，並至少包含：

```json
{
  "version": 1,
  "type": "commit",
  "sessionId": "random-session-id",
  "round": 1,
  "messageId": "random-message-id",
  "payload": {}
}
```

訊息類型：

- `hello`：交換協定版本、玩家顯示名稱與主客角色。
- `commit`：傳送本回合選擇的 SHA-256 hash。
- `reveal`：傳送選擇與 nonce，供對方驗證。
- `round-result`：傳送本地計算的單把結果，供雙方比對。
- `next-round`：玩家已選擇「下一把」；收到雙方的選擇後才開始新回合。
- `leave`：主動離開遊戲。
- `error`：協定、驗證或狀態錯誤。
- `ping` / `pong`：檢查連線是否仍然有效。

收到訊息時必須先檢查 schema、`sessionId`、`round` 與當前狀態。重複的 `messageId` 應忽略，不得重複處理回合結果或「下一把」選擇。

### 3.7 Commit-Reveal 公平性機制

玩家選擇後不直接傳送拳種，而是先傳送無法反推的承諾值。

```text
commit = SHA-256(
  protocolVersion + "|" +
  sessionId + "|" +
  round + "|" +
  choice + "|" +
  nonce
)
```

規則：

1. `choice` 必須是 `rock`、`paper` 或 `scissors`。
2. `nonce` 必須由 `crypto.getRandomValues()` 產生，建議至少 128 bits。
3. 雙方都收到對方的 `commit` 後，才能傳送 `reveal`。
4. 收到 `reveal` 後重新計算 hash，並與先前的 `commit` 比對。
5. 驗證失敗時立即終止本場遊戲，顯示「對手資料驗證失敗」，不更新正常戰績。

此機制可防止對手看到出拳後才更改選擇，但無法防止對手在預期輸掉時斷線。

### 3.8 遊戲狀態機

```text
idle
  -> creating-offer / importing-offer
  -> waiting-answer / creating-answer
  -> connecting
  -> choosing
  -> committed
  -> revealing
  -> round-result
  -> waiting-next-round
  -> choosing（雙方都選擇下一把）

任一連線狀態
  -> disconnected
  -> closed
```

每個狀態只允許預期的事件。例如，在未收到雙方 `commit` 前收到 `reveal`，應視為協定錯誤。

### 3.9 本地資料

默認不必保存任何資料。若要改善使用體驗，可用 `localStorage` 保存：

- 玩家顯示名稱。
- 音效與動畫偏好。
- 本機勝敗統計，但不得將其表示為可驗證的線上戰績。

不得將當前回合 nonce 或未公開的選擇持久化。

## 4. 遊戲流程

### 4.1 建立與加入遊戲

#### 主機

1. 開啟首頁配對畫面。
2. 點選「建立遊戲」。
3. 等待系統產生 Offer。
4. 讓對方掃描邀請網址 QR Code，或複製邀請網址傳給對方。
5. 掃描或貼上對方產生的 Answer。
6. 等待顯示「連線成功」。

#### 加入者

1. 開啟首頁配對畫面。
2. 點選「加入遊戲」。
3. 開啟主機的邀請網址；頁面會自動匯入 Offer。
4. 等待系統產生 Answer。
5. 讓主機掃描 Answer QR Code，或複製 Answer 回傳給主機。
6. 等待顯示「連線成功」。

### 4.2 對戰流程

1. DataChannel 連線成功並完成 `hello` 版本檢查後，系統直接進入對戰畫面。
2. 系統顯示剪刀、石頭、布三個選擇。
3. 玩家選擇拳種；確認後本把不可反悔。
4. 前端產生 nonce 與 commit，只將 commit 傳給對手。
5. 當雙方 commit 都已到達，前端交換 choice 與 nonce。
6. 兩端分別驗證對手的 commit。
7. 驗證通過後，兩端使用相同規則計算勝負。
8. 顯示雙方拳種與本把結果，同時提供「下一把」與「退出」。
9. 任一方選擇「下一把」後，界面顯示「等待對手選擇」，且不得先進入出拳畫面。
10. 雙方都選擇「下一把」時，回合編號加 1，清除上一把的 choice、nonce 與 commit，開始新的一把。
11. 任一方選擇「退出」時，傳送 `leave` 並關閉連線；對方收到後回到首頁配對畫面。

### 4.3 異常流程

- **配對資料錯誤**：顯示可理解的原因，允許重新掃描或貼上，不得執行不完整資料。
- **連線逾時**：提示更換網路或重新建立遊戲。
- **遊戲中斷線**：立即停止回合計時與互動，顯示對手已斷線。MVP 不嘗試恢復原連線。
- **commit 驗證失敗**：終止當前連線，將本把標記為無效對局。
- **對手長時間無回應**：顯示等待狀態；超過 30 秒後允許玩家結束遊戲。
- **協定版本不相容**：不開始對戰，提示雙方使用同一版本。

## 5. 遊戲規則

### 5.1 基本規則

每局兩位玩家各選擇一種拳：

- **剪刀（scissors）**：剪刀剪破布。
- **石頭（rock）**：石頭擊敗剪刀。
- **布（paper）**：布包住石頭。

勝負對照：

| 玩家 A | 玩家 B | 結果 |
| --- | --- | --- |
| 剪刀 | 剪刀 | 平手 |
| 剪刀 | 石頭 | B 勝 |
| 剪刀 | 布 | A 勝 |
| 石頭 | 剪刀 | A 勝 |
| 石頭 | 石頭 | 平手 |
| 石頭 | 布 | B 勝 |
| 布 | 剪刀 | B 勝 |
| 布 | 石頭 | A 勝 |
| 布 | 布 | 平手 |

### 5.2 單把與繼續規則

- 每把都是獨立對局，不計算系列賽分數。
- 一把結束後，雙方分別選擇「下一把」或「退出」。
- 只有雙方都選擇「下一把」時，才能開始新的一把。
- 一方已選擇「下一把」而另一方尚未選擇時，必須留在結果畫面等待。
- 任一方選擇「退出」，本次對戰立即結束，雙方回到首頁配對畫面。
- 開始下一把前，必須清除上一把的選擇、nonce、commit、reveal 與繼續狀態。

### 5.3 選擇與公開規則

- 玩家可在按下「確認出拳」前更改選擇。
- 送出 commit 後不得更改本把選擇。
- 當對手尚未 commit 時，界面只顯示「等待對手」，不公開任何拳種。
- 只有在雙方 commit 都收到後，才能公開選擇。
- 雙方都應獨立計算結果；若結果不一致，該場應停止並顯示協定錯誤。

### 5.4 斷線與棄權

- 玩家主動按下離開時，應先嘗試傳送 `leave` 訊息。
- 收到 `leave` 的玩家可將對手顯示為離開，但純 P2P 模式不能產生可對外驗證的棄權戰績。
- 網路中斷與關閉頁面不一定能區分，因此 MVP 統一顯示為「對手已斷線」。
- 斷線後若要繼續，雙方需回到首頁重新建立連線，並開始新的一把。

## 6. 介面與使用體驗

### 6.1 主要畫面

1. **首頁／配對畫面**：整合建立遊戲、加入遊戲、QR Code、掃描器、複製貼上區、配對進度、取消按鈕與玩法說明。不另設獨立配對頁。
2. **對戰畫面**：對手名稱、連線狀態、回合數、三種拳、確認按鈕與對手等待狀態。連線完成後直接進入，不另設大廳。
3. **單把結果畫面**：雙方拳種、勝負動畫、「下一把」與「退出」按鈕，以及對手是否已選擇繼續的狀態。不設系列賽結果頁。

### 6.2 顯示原則

- 行動裝置應能單手操作，主要按鈕觸控區至少 44 × 44 CSS pixels。
- 不只使用顏色表達勝負或連線狀態，同時顯示文字與圖示。
- 按鈕、狀態與錯誤訊息應有鍵盤操作與輔助技術標籤。
- 遵循 `prefers-reduced-motion`，必要時降低或關閉動畫。
- 配對資料輸入錯誤時保留原輸入，便於玩家修正。

## 7. 安全與隱私

- 只接受符合預定 schema 的 JSON 訊息，拒絕未知欄位中的可執行內容。
- 不將對方傳入文字以 `innerHTML` 插入頁面，應使用 `textContent`。
- 限制配對封包、顯示名稱與 DataChannel 訊息的長度。
- 配對封包可含 IP 連線候選資訊；應在畫面上提示玩家只與可信任對象交換。
- 關閉頁面、取消配對或離開遊戲時，關閉 DataChannel 與 `RTCPeerConnection`，並清除回合 nonce。
- 遊戲不要求相機以外的裝置權限；只在玩家主動啟動掃描時請求相機權限。

## 8. 驗收標準

### 8.1 連線

- 兩台不同裝置可以透過 QR Code 或複製貼上完成 Offer / Answer 交換。
- 雙方頁面部署在不同 HTTPS 網域時，仍可建立 DataChannel。
- DataChannel 開啟後，雙方能正確交換 `hello`，並直接進入對戰畫面。
- 不合法、過期或版本不相容的配對封包會被拒絕。
- 拒絕相機權限後，仍可以複製貼上完成連線。

### 8.2 遊戲邏輯

- 九種剪刀石頭布組合皆產生正確結果。
- 送出 commit 後無法更改選擇。
- 未收到雙方 commit 前不會送出 reveal。
- 修改 choice 或 nonce 後，commit 驗證必須失敗。
- 重複或過期回合訊息不會導致重複顯示結果或跳過回合。
- 單把結束後不自動開始下一把。
- 只有雙方都選擇「下一把」時，才進入新回合。
- 任一方選擇「退出」時，雙方均結束對戰並回到首頁配對畫面。
- 雙方對同一組 reveal 資料得出一致結果。

### 8.3 異常與使用性

- 對手離開、DataChannel 關閉或連線失敗時，界面不會停留在可繼續出拳的狀態。
- 配對、等待、已送出、驗證中、勝負與斷線都有明確文字提示。
- 界面可在常見行動裝置寬度下完整操作，無水平滾動與重疊。
- 主要功能可使用鍵盤操作，焦點指示清楚可見。

## 9. 已知限制與後續方向

### 9.1 已知限制

- 無 TURN 時不能保證所有網路都能連線。
- 手動交換 Offer / Answer 比房號配對多一些步驟。
- 連線中斷後無法從原進度可信地恢復。
- 純前端無法建立可驗證的全域戰績與排行榜。
- commit-reveal 可防止改拳，但無法防止故意斷線或修改畫面顯示。

### 9.2 可選後續功能

- 以極小型 signaling 服務提供房號或邀請連結。
- 加入 TURN 服務以提高連線成功率。
- 增加限時出拳與本機遊戲歷程。
- 加入可安裝的 PWA 與離線載入。
- 加入音效、觸覺回饋與更完整的動畫。
- 將協定與遊戲規則抽成獨立模組，以自動化測試保證不同網域版本的相容性。
